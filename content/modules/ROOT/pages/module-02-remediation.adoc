= Module 2: Orchestrate — AO Update Workflow

== Module Overview

In this module, you'll watch Automation Orchestrator execute the full update workflow: committing the dependency bump to Git, monitoring the Tekton build pipeline, and watching ArgoCD deploy the result to OpenShift.

**Learning Objectives:**

* See how Automation Orchestrator acts on Concert's impact data
* Watch a Tekton PipelineRun build, test, and publish a container image
* Understand how ArgoCD GitOps delivers the change to the cluster
* Validate the deployment against the running application

**Estimated time**: 20 minutes

== Where the Workflow Picks Up

The workflow from Module 1 continues now with the update phase. Concert has told Automation Orchestrator what is affected and what it touches; the switch node has routed `flask-api-app` to auto-update.

Navigate back to the Automation Orchestrator workflow you opened in Module 1 —
`Lightwell Proactive Update` for your lab ID. Each AAP Job node in it launches a
job template on your own Automation Controller, so you can follow along in either
place.

[NOTE]
====
There is no "fetch the Lightwell artifact" step in this workflow. The artifact ID, URL, and checksum arrived in the Artifactory event that started everything — the provenance travels with the trigger, so there is nothing left to look up.
====

== Step 1: Update the Dependency in Git

The first execution node runs `lab/playbooks/aap/update-dependency-git.yml`. It clones the application repository, creates a branch, bumps the pin, and pushes.

[source,text]
----
TASK [Clone application repository]
changed: [localhost]

TASK [Create update branch]
changed: [localhost]

TASK [Update requirements.txt with Lightwell package version]
changed: [localhost]

TASK [Commit changes]
changed: [localhost]

TASK [Push branch to origin]
changed: [localhost]

TASK [Set stats for AAP workflow]
ok: [localhost] => {
    "git_branch": "lightwell-update/pyyaml-6.0.2",
    "git_commit_sha": "a1b2c3d4e5f67890",
    "commit_message": "Update pyyaml to Lightwell remediated version 6.0.2 (fixes CVE-2026-52891)"
}
----

The change itself is a single line:

[source,diff]
----
 flask==2.3.2
-pyyaml==5.4.1
+pyyaml==6.0.2  # Lightwell remediated package
 requests==2.31.0
----

**Red Hat Lightwell** is what makes that one-line change safe to automate. Lightwell provides:

* **Remediated dependencies**: Packages with CVE fixes applied
* **Verification**: Cryptographically signed packages with checksum verification
* **Compatibility testing**: Red Hat tested to ensure no breaking changes
* **Audit trail**: Complete provenance from source to package

This is safer than blindly upgrading to the latest PyPI version, which might introduce breaking API changes, pull in unvetted transitive dependencies, or lack enterprise support.

The commit SHA is captured into workflow stats — the next node needs it to find the right pipeline run.

== Step 2: Watch the Tekton Pipeline

The git push fires a Tekton `EventListener`, which creates a `PipelineRun` labelled with the commit SHA.

. Click the **OpenShift** tab in the workshop sidebar.

. Navigate to **Pipelines** → **PipelineRuns**, and select the `ci-cd` project.

. Find the run named `flask-api-app-build-*` that was just created. Click it to watch the tasks execute:

**Pipeline Tasks**:

[source,text]
----
git-clone        ✓ Clone repository at commit a1b2c3d4
run-tests        ✓ pytest — unit and integration tests
build-image      ✓ buildah build with pyyaml 6.0.2
push-image       ✓ Push quay.io/labuser/flask-api-app:a1b2c3d4
update-gitops    ✓ Update image tag in GitOps manifest
----

You can follow the same run from the Terminal:

[source,bash]
----
tkn pipelinerun logs --last -f -n ci-cd
----

Note the final task. Tekton does **not** deploy the application. It builds, tests, publishes an image, and then updates a manifest in the GitOps repository. Delivery is ArgoCD's job — which keeps the cluster's desired state in Git rather than in a pipeline script.

== Step 3: Automation Orchestrator Monitors the PipelineRun

Switch back to Automation Controller. The `Lightwell - Monitor Tekton Pipeline` node runs `lab/playbooks/aap/monitor-tekton-pipeline.yml` and polls the PipelineRun to completion:

[source,text]
----
TASK [Find PipelineRun for this commit]
ok: [localhost] => (attempt 2/12)

TASK [Wait for PipelineRun to complete]
ok: [localhost] => (attempt 9/60)

TASK [Assert pipeline succeeded]
ok: [localhost] => {
    "msg": "Tekton PipelineRun flask-api-app-build-xk29f succeeded"
}

TASK [Display pipeline results]
ok: [localhost] => {
    "tekton_pipelinerun": "flask-api-app-build-xk29f",
    "tekton_status": "success",
    "container_image": "quay.io/labuser/flask-api-app:a1b2c3d4"
}
----

The playbook matches the PipelineRun by the `lightwell/commit-sha` label, so it tracks exactly the run its own commit produced — not whichever run happened to start most recently.

If the pipeline fails, the assertion fails, the workflow stops, and no deployment occurs. Tests are a gate, not a formality.

== Step 4: Watch ArgoCD Deploy

Tekton's final task committed a new image tag to the GitOps repository. ArgoCD notices within seconds.

. In the **OpenShift** tab, open the **ArgoCD** console (or the *Cluster Argo CD* link from the GitOps operator).

. Find the `flask-api-app` Application and watch it sync:

[source,text]
----
Application: flask-api-app
Sync Status:   OutOfSync → Syncing → Synced
Health Status: Progressing → Healthy
Revision:      b7e4f21 (gitops repo)

Resources:
  Deployment/flask-api-app   Synced   Healthy
  Service/flask-api-app      Synced   Healthy
  Route/flask-api-app        Synced   Healthy
----

Because the Application has `syncPolicy.automated` enabled, no one clicked anything. ArgoCD detected drift between Git and the cluster and closed the gap.

. Watch the rolling update from the Terminal:
+
[source,bash]
----
oc rollout status deployment/flask-api-app -n production
----

The Deployment rolls 3 replicas one at a time. At no point are all pods down.

== Step 7: Understanding the Complete Workflow

Let's review what Automation Orchestrator did:

[source,text]
----
1. Artifactory Event
   └─> Lightwell published pyyaml 6.0.2
   └─> EDA rulebook triggered AO workflow

2. Concert Impact Analysis (Module 1)
   └─> SBOM query: 12 of 537 apps on older version
   └─> Arena View: production deployment, 1 downstream dependency

3. AO Routing Decision (Module 1)
   └─> Production + critical severity → auto-update

4. Update Source Control
   └─> Branch lightwell-update/pyyaml-6.0.2
   └─> requirements.txt: pyyaml 5.4.1 → 6.0.2
   └─> Commit and push

5. Tekton PipelineRun
   └─> git-clone → run-tests → build-image
   └─> push-image → quay.io/labuser/flask-api-app:a1b2c3d4
   └─> update-gitops manifest

6. ArgoCD GitOps Sync
   └─> Detected manifest drift
   └─> Rolling update, 3 replicas
   └─> Synced / Healthy

7. Validate Deployment
   └─> ArgoCD sync and health
   └─> 3/3 pods ready, image matches
   └─> /health reports pyyaml 6.0.2

8. Update Concert Inventory
   └─> SBOM patched, portfolio drift 12 → 11
----

**Total time from package publish to validated deployment**: ~3 minutes

**Without automation**:

* Someone notices the new package: days to weeks
* Development team updates the pin: 1-2 days
* QA testing: 1-2 days
* Change approval process: 1-3 days
* Deployment scheduling: 1-5 days
* **Total**: 5-14 days — per application, times 12

== Why Tekton and ArgoCD

The CI/CD split in this lab is deliberate, and it changes what the automation can promise.

**Tekton owns build-time**: cloning, testing, building, and publishing an immutable, digest-addressable image. It runs on the cluster, as pods, with no external runners to maintain.

**ArgoCD owns run-time**: the cluster's desired state lives in Git. That yields three things a push-based pipeline cannot easily offer:

* **Drift detection** — if someone edits the Deployment by hand, ArgoCD reports it and (with `selfHeal`) reverts it
* **Rollback as a first-class operation** — `argocd app rollback` returns to any prior synced revision
* **A single source of truth** — the answer to "what should be running?" is a Git commit, not a pipeline log

[TIP]
====
Try a rollback to see this. From the Terminal:
[source,bash]
----
argocd app history flask-api-app
argocd app rollback flask-api-app <previous-revision>
----
The cluster returns to PyYAML 5.4.1 in seconds — and ArgoCD will report the Application as `OutOfSync` against Git until you either re-sync or revert the commit.
====

== Alternative Path: Approval Gates

In this lab, the switch node routed straight to auto-update because the target had a production deployment and the package was marked critical.

Had Concert's Arena View reported downstream dependencies owned by another team without a critical severity to justify the risk, AO would have taken a different branch:

1. **Create an approval request** — AAP workflow approval node, or a ticket in an external system
2. **Notify the owning teams** — `platform-team` for the app, `network-team` for `api-gateway`
3. **Wait for human sign-off** — the workflow pauses, holding all its Concert context
4. **Resume on approval** — the same Tekton and ArgoCD path executes unchanged

This gives you **graduated autonomy**: fully automated where the risk profile allows it, human-gated where it doesn't, with identical delivery machinery behind both.
