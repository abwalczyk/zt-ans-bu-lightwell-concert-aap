= Module 3: Validate — Audit Trail

== Module Overview

In this module, you'll review the complete audit trail across all systems involved in the update. This demonstrates compliance and accountability for automated dependency management.

**Learning Objectives:**

* Review Concert's updated SBOM inventory
* Understand the complete audit trail across systems
* See how automated updates maintain compliance

**Estimated time**: 10 minutes

== The Importance of Audit Trails

Automated updates are powerful, but enterprises need accountability and compliance:

* **Regulatory requirements**: SOC 2, ISO 27001, PCI DSS require audit trails for security changes
* **Change management**: Track who/what made changes, when, and why
* **Incident response**: Investigate if an update caused issues
* **Compliance reporting**: Prove to auditors that known vulnerabilities were addressed

This lab demonstrates **end-to-end auditability** across:

* Artifactory package publication
* Event-Driven Ansible
* Automation Orchestrator
* IBM Concert
* Git source control
* Tekton pipelines
* ArgoCD GitOps delivery
* Application runtime

Note that this chain has a property the reactive model lacks: it starts with a *signed, verified artifact*, not an alert. The provenance of the fix is part of the evidence.

== Step 2: Artifactory Package Provenance

The chain of evidence begins before any automation ran. In Artifactory, locate the published artifact:

[source,text]
----
Repository:   lightwell-remediated
Artifact:     pyyaml-6.0.2.rhlw-00456
Published:    2026-09-25 14:20:31 UTC
Checksum:     sha256:abc123def456
Fixes:        CVE-2026-52891 (critical)
Signed by:    Red Hat Lightwell
----

This proves:

* **What**: The exact artifact, identified by immutable checksum
* **From**: Red Hat Lightwell, cryptographically signed
* **Why**: The CVE the build remediates
* **When**: The moment the fix became available to the organization

The checksum here is the same value carried in the EDA event payload and recorded in the AAP job variables — one identifier spans the whole trail.

== Step 7: ArgoCD Sync History

In the ArgoCD console, open the `flask-api-app` Application and select **History and Rollback**.

[source,text]
----
Application: flask-api-app
Project:     default
Source:      https://github.com/labuser/flask-api-app-gitops
Path:        apps/flask-api-app/overlays/production

Sync History:
  Revision b7e4f21  2026-09-25 14:22:55 UTC  Succeeded  (current)
    └─> image: quay.io/labuser/flask-api-app:a1b2c3d4
  Revision 3c1a890  2026-09-18 09:14:02 UTC  Succeeded
    └─> image: quay.io/labuser/flask-api-app:7f2e1d9

Sync Policy: Automated (prune: true, selfHeal: true)
Current Status: Synced / Healthy
----

This is the part a push-based pipeline cannot give you. The GitOps repository is a complete, ordered record of every state the cluster has been asked to hold — and each entry is a rollback target.

This proves:

* **Desired state**: What Git said should be running, at every point in time
* **Actual state**: ArgoCD's continuous reconciliation confirms the cluster matches
* **Drift protection**: `selfHeal` means manual cluster edits are reverted and visible
* **Recoverability**: Any prior revision can be restored as a single operation

== Step 8: Application Runtime Validation

Finally, verify the running application from the **Flask App** tab (`/health`) or the **Terminal** tab:

[source,bash]
----
curl -s https://$(oc get route flask-api-app -n production -o jsonpath='{.spec.host}')/health
----

Response:
[source,json]
----
{
  "app": "flask-api",
  "status": "ok",
  "pyyaml_version": "6.0.2"
}
----

And confirm the pods are running the expected image:

[source,bash]
----
oc get pods -n production -l app=flask-api-app \
  -o jsonpath='{.items[*].spec.containers[0].image}'
----

The application is running the remediated version across all 3 replicas.

== Compliance Benefits

This audit trail satisfies compliance requirements:

**SOC 2 / ISO 27001**:

* Evidence of timely vulnerability remediation
* Automated controls reduce human error
* Complete change history with timestamps
* Signed artifact provenance from the upstream vendor

**PCI DSS**:

* Critical vulnerabilities remediated within required timeframes
* Audit logs show who/what made changes
* Testing performed before deployment, enforced as a gate

**Change Management**:

* Automated routing based on Concert deployment and topology data
* Code review via Git history
* Rollback capability via ArgoCD revision history, not manual re-deploy

**Incident Response**:

* If issues arise, full timeline available
* Exact image digest deployed is tracked
* Single-command rollback to any prior synced revision
