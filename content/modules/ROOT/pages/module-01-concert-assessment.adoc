= Module 1: Concert Vulnerability Assessment

== Module Overview

In this module, you'll trigger a CVE alert from a security scanner and watch how IBM Concert identifies affected applications through its SBOM inventory and assesses the vulnerability's impact.

**Learning Objectives:**

* Understand how Event-Driven Ansible receives CVE alerts
* See how Concert identifies affected applications from SBOM data
* Learn how Concert assesses application impact and risk

**Estimated time**: 15 minutes

== Lab tabs you will use

Use the workshop sidebar tabs for each step:

* **Flask App** — vulnerable application on `rhel01` (route host `app`)
* **AAP** — Automation Controller on `control`
* **Terminal** — SSH session on `control` (run `curl` commands here)
* **Gitea** — Git repository and CI/CD
* **Concert** — shared Concert UI

== The Scanner Overload Problem

Modern security scanners like Mythos, Trivy, and others produce thousands of vulnerability alerts. In a typical enterprise environment:

* **Scanner Output**: 5,000+ vulnerabilities detected across your application portfolio
* **False Positive Rate**: 99.9% of alerts are duplicates, not-exploitable, or not-applicable
* **Manual Triage**: Takes security teams days or weeks to identify which vulnerabilities actually matter

**Concert's Solution**: Concert correlates scanner alerts with your enterprise SBOM inventory. Instead of manually checking 5,000 alerts, Concert instantly identifies the 12 vulnerabilities that are actually deployed in running applications.

== Step 1: View the Vulnerable Application

First, verify that the Flask application is running with the vulnerable PyYAML version.

. Click the **Flask App** tab in the workshop sidebar.
+
This opens the application exposed from `rhel01` via the `app` route in `config/instances.yaml`.

. Append `/version` to the URL in the address bar (or open that path directly) so you land on the version endpoint.
+
Alternatively, open the **Terminal** tab and run:
+
[source,bash]
----
curl http://rhel01/version
----
+
From the Terminal on `control`, `rhel01` resolves on the lab secondary network.

Expected output:

[source,json]
----
{
  "app": "flask-api",
  "pyyaml_version": "5.4.1"
}
----

This confirms the application is using PyYAML 5.4.1, which contains CVE-2026-52891 (CVSS 9.8 - Critical).

==== Verify

* The **Flask App** tab loads the application JSON (or `/version` returns the payload above)
* PyYAML version is `5.4.1`

== Step 2: Open Automation Controller and find the EDA activation

Your security scanner (Mythos) has detected CVE-2026-52891 and will send a webhook to Event-Driven Ansible.

. Click the **AAP** tab in the workshop sidebar.

. Log in with:
+
* Username: `admin`
* Password: `ansible123!`

. In the left navigation, open **Automation Decisions** (Event-Driven Ansible) → **Rulebook Activations**.

. Confirm the activation exists and is running:
+
* **Activation Name**: `cve-scanner-webhook`
* **Status**: Running
* **Description**: Receives CVE alerts from security scanners

This EDA activation listens for incoming CVE webhooks on port `5000` on the `control` host (service `eda-webhook` in `config/instances.yaml`).

==== Verify

* You can sign in to Automation Controller
* Activation `cve-scanner-webhook` shows **Running**

== Step 3: Simulate Scanner Alert

In the real world, your security scanner would send this webhook automatically. For this lab, simulate it from the Terminal on `control`.

. Click the **Terminal** tab.

. Run:

[source,bash]
----
curl -X POST http://localhost:5000/webhook \
  -H "Content-Type: application/json" \
  -d '{
    "cve_id": "CVE-2026-52891",
    "severity": "CRITICAL",
    "cvss_score": 9.8,
    "package": "PyYAML",
    "vulnerable_versions": "< 6.0.0",
    "scanner": "Mythos",
    "timestamp": "2026-09-17T10:30:00Z"
  }'
----

Expected output:

[source,json]
----
{
  "status": "received",
  "message": "CVE alert queued for processing"
}
----

==== Verify

* The `curl` command returns a received/queued response

== Step 4: Watch Event-Driven Ansible Trigger Automation Orchestrator

. Return to the **AAP** tab.

. Navigate to **Automation Decisions** → **Rulebook Activations** → **cve-scanner-webhook** → **Instances** / **History** (wording may vary slightly by AAP version).

. Find the new event for CVE-2026-52891. You should see something like:
+
* **Event**: CVE-2026-52891 received
* **Action**: Triggered job / workflow `CVE Remediation Workflow`
* **Timestamp**: Just now

. Click the linked job to open the Automation Orchestrator workflow run.

==== Verify

* A new activation event/history entry appears after the webhook
* A related Controller job/workflow was launched

== Step 5: Automation Orchestrator Queries Concert

. In the **AAP** tab, open **Automation Execution** → **Jobs**.

. Open the **CVE Remediation Workflow** job that was just triggered.

. Watch the job output. You should see tasks similar to:

[source,text]
----
TASK [Query Concert for affected applications]
ok: [localhost]

TASK [Display Concert assessment]
ok: [localhost] => {
    "concert_assessment": {
        "cve_id": "CVE-2026-52891",
        "affected_apps": [
            {
                "name": "flask-api",
                "host": "rhel01",
                "current_version": "5.4.1",
                "sbom_id": "flask-api-v1.0.0",
                "deployment": "production",
                "risk_score": 95
            }
        ],
        "total_apps_scanned": 487,
        "affected_count": 1,
        "concert_recommendation": "REMEDIATE_IMMEDIATELY"
    }
}
----

**Key Concert Capabilities Demonstrated:**

* **SBOM Correlation**: Concert scanned its inventory of 487 applications and identified 1 affected app
* **Risk Assessment**: Concert calculated a risk score of 95/100 based on:
  - CVE severity (CVSS 9.8)
  - Application criticality (production deployment)
  - Exploitability (publicly known exploit)
  - Exposure (internet-facing API)
* **Actionable Intelligence**: Concert recommended immediate remediation

Without Concert, you would need to manually:

1. Query all 487 applications for their Python dependencies
2. Check each application's PyYAML version
3. Assess which deployments are production vs. dev/test
4. Prioritize based on risk and exposure

Concert did this instantly by querying its pre-indexed SBOM database.

Optionally open the **Concert** tab to explore the shared Concert UI while the workflow runs.

== Step 6: Review Concert Action Center

The workflow job pauses here and displays Concert's assessment. In a real Concert deployment, you could also view this in Concert's Action Center UI:

**Concert Action Center** shows:

* **CVE**: CVE-2026-52891
* **Affected Applications**: 1 (flask-api)
* **Risk Score**: 95 (Critical)
* **Recommended Action**: Remediate immediately
* **Available Solutions**:
  - Lightwell remediated package available (PyYAML 6.0.2)
  - Concert Secure Coder can generate code changes

This is the intelligence that drives the automated remediation in Module 2.

== Module Summary

You've completed Module 1! Here's what happened:

1. **Security scanner detected CVE** → Sent webhook to EDA
2. **Event-Driven Ansible received alert** → Triggered Automation Orchestrator workflow
3. **Automation Orchestrator queried Concert** → "Which apps are affected?"
4. **Concert assessed impact** → Identified 1 app out of 487, risk score 95
5. **Concert provided actionable intelligence** → Remediate immediately, Lightwell package available

**The Value of Concert**:

* **Speed**: Instant identification of affected apps (seconds vs. hours)
* **Accuracy**: SBOM-based correlation eliminates false positives
* **Context**: Risk scoring considers deployment environment and exploitability
* **Actionability**: Recommendations tied to available remediation paths
