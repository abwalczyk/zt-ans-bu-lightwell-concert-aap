= Module 1: Detect — Package Publish & Concert Impact Analysis

== Module Overview

In this module, you'll publish a new Lightwell remediated package to Artifactory and watch how IBM Concert instantly identifies every application in the portfolio still running an older version.

**Learning Objectives:**

* Understand how Event-Driven Ansible reacts to a new Lightwell package event
* See how Concert identifies affected applications from SBOM data, queried by package
* Learn how Concert's Arena View topology exposes cross-team deployment impact

**Estimated time**: 15 minutes

== Lab tabs you will use

Use the workshop sidebar tabs for each step:

* **Flask App** — target application route on OpenShift
* **AAP** — Automation Controller on `control`
* **Terminal** — SSH session on `control` (run `curl` and `oc` commands here)
* **OpenShift** — cluster console for Tekton and ArgoCD
* **Concert** — shared Concert UI

== From Reactive to Proactive

Most vulnerability automation is reactive: a scanner finds a problem, and a workflow scrambles to fix it. That model has a structural weakness — the clock starts when the *problem* is discovered, and you are always behind.

This lab inverts the trigger. The clock starts when the *fix* becomes available.

* **Lightwell publishes** a remediated package into Artifactory's `lightwell-remediated` repository
* **Artifactory fires a webhook** describing the package and what it fixes
* **Concert answers** the only question that matters: which of our 537 applications are still on an older version?

Instead of chasing 5,000 scanner alerts, you act on a single trusted, verified artifact and fan it out across every application that needs it.

== Step 1: View the Current Application State

First, verify that the Flask application is running with the older PyYAML version.

. Click the **Flask App** tab in the workshop sidebar.
+
This opens the application route served by the `flask-api-app` Deployment in the `production` namespace.

. Append `/health` to the URL in the address bar (or open that path directly) so you land on the health endpoint.
+
Alternatively, open the **Terminal** tab and run:
+
[source,bash]
----
curl -s https://$(oc get route flask-api-app -n production -o jsonpath='{.spec.host}')/health
----

Expected output:

[source,json]
----
{
  "app": "flask-api",
  "status": "ok",
  "pyyaml_version": "5.4.1"
}
----

This confirms the application is using PyYAML 5.4.1 — the version Lightwell has just superseded.

. Confirm the deployment is healthy before you begin:
+
[source,bash]
----
oc get pods -n production -l app=flask-api-app
----
+
You should see 3 pods in `Running` state.

==== Verify

* The **Flask App** tab loads the application JSON (or `/health` returns the payload above)
* PyYAML version is `5.4.1`
* 3 of 3 pods are `Running`

== Step 2: Open Automation Controller and find the EDA activation

Artifactory will send a webhook to Event-Driven Ansible when the new Lightwell package is published.

. Click the **AAP** tab in the workshop sidebar.

. Log in with:
+
* Username: `admin`
* Password: `ansible123!`

. In the left navigation, open **Automation Decisions** (Event-Driven Ansible) → **Rulebook Activations**.

. Confirm the activation exists and is running:
+
* **Activation Name**: `artifactory-lightwell-webhook`
* **Status**: Running
* **Description**: Receives new Lightwell package events from Artifactory

This EDA activation runs the rulebook `extensions/eda/rulebooks/lightwell-package-alert.yml` and listens on port `5000` on the `control` host (service `eda-webhook` in `config/instances.yaml`).

The rulebook condition is deliberately narrow — it only fires for packages published into a Lightwell repository:

[source,yaml]
----
condition: >-
  event.payload.package_name is defined and
  event.payload.package_version is defined and
  event.payload.repository is search("lightwell")
----

==== Verify

* You can sign in to Automation Controller
* Activation `artifactory-lightwell-webhook` shows **Running**

== Step 3: Simulate the Artifactory Package Publish

In production, Artifactory sends this webhook automatically when Lightwell pushes a new build. For this lab, simulate it from the Terminal on `control`.

. Click the **Terminal** tab.

. Run:

[source,bash]
----
curl -X POST http://localhost:5000/webhook \
  -H "Content-Type: application/json" \
  -d '{
    "package_name": "pyyaml",
    "package_version": "6.0.2",
    "previous_version": "5.4.1",
    "target_app": "flask-api-app",
    "artifact_id": "pyyaml-6.0.2.rhlw-00456",
    "artifact_url": "https://artifactory.example.com/lightwell-remediated/pyyaml-6.0.2.rhlw-00456",
    "checksum": "sha256:abc123def456",
    "repository": "lightwell-remediated",
    "remediation_info": {
      "fixes_cve": "CVE-2026-52891",
      "severity": "critical"
    }
  }'
----

Expected output:

[source,json]
----
{
  "status": "received",
  "message": "Lightwell package event queued for processing"
}
----

Note what this payload carries: the artifact ID, URL, and checksum are all present in the event itself. There is no separate Lightwell API lookup step later in the workflow — the provenance travels with the trigger.

==== Verify

* The `curl` command returns a received/queued response

== Step 4: Watch Event-Driven Ansible Trigger Automation Orchestrator

. Return to the **AAP** tab.

. Navigate to **Automation Decisions** → **Rulebook Activations** → **artifactory-lightwell-webhook** → **Instances** / **History** (wording may vary slightly by AAP version).

. Find the new event for the pyyaml package. You should see something like:
+
* **Event**: pyyaml 6.0.2 published to `lightwell-remediated`
* **Action**: Ran job template `AO - Trigger Proactive Update Workflow`
* **Timestamp**: Just now

. Click the linked job. It is a one-task relay: it POSTs the package event to the
  Automation Orchestrator webhook. The job output prints the AO workflow URL.

. Open that URL to watch the Automation Orchestrator workflow run.
+
[NOTE]
====
EDA Controller cannot call an HTTP endpoint directly — its rulebook actions launch
templates, not requests. That is why the handoff to AO is a job template rather
than a single hop. The upside is that the handoff shows up in the AAP job list,
which is the first place to look if AO never starts.
====

==== Verify

* A new activation event/history entry appears after the webhook
* A related Controller workflow was launched

== Step 5: Automation Orchestrator Queries Concert SBOM Inventory

. In the **AAP** tab, open **Automation Execution** → **Jobs**.

. Open the **Concert - Query SBOM Inventory** job node inside the running workflow.

This node runs `lab/playbooks/concert/query-sbom-by-package.yml`, which queries Concert *by package* rather than by CVE:

[source,text]
----
GET /api/v1/inventory/packages/pyyaml/applications
Body: { "older_than": "6.0.2" }
----

. Watch the job output. You should see tasks similar to:

[source,text]
----
TASK [Query Concert inventory for applications using this package]
ok: [localhost]

TASK [Display Concert SBOM inventory results]
ok: [localhost] => {
    "msg": "==========================================
      Concert SBOM Inventory Results
      ==========================================
      New Lightwell Package: pyyaml 6.0.2

      PORTFOLIO-WIDE IMPACT:
      Applications on an older version: 12
      (Concert scanned 537 apps)

      TARGET APPLICATION:
      Name: flask-api-app
      Found in affected list: YES
      Current Version: 5.4.1
      Owner Team: platform-team
      Repository: https://github.com/labuser/flask-api-app
      =========================================="
}
----

**Key Concert Capabilities Demonstrated:**

* **SBOM Correlation**: Concert scanned its inventory of 537 applications and identified 12 still on an older PyYAML
* **Package-centric query**: One published artifact resolves to a complete work queue, instantly
* **Ownership context**: Each affected application carries its owning team, so the update can be routed correctly

Without Concert, you would need to manually:

1. Query all 537 applications for their Python dependencies
2. Check each application's PyYAML version against 6.0.2
3. Determine which deployments are production vs. dev/test
4. Identify who owns each application

Concert did this instantly by querying its pre-indexed SBOM database.

Optionally open the **Concert** tab to explore the shared Concert UI while the workflow runs.

== Step 6: Review Concert Arena View Topology

The workflow's next node runs `lab/playbooks/concert/query-topology.yml`, which asks Concert a different question: what will this change touch?

[source,text]
----
GET /api/v1/arena/applications/flask-api-app/topology
----

[source,text]
----
TASK [Display Concert topology results]
ok: [localhost] => {
    "msg": "==========================================
      Concert Arena View Topology
      ==========================================
      Application: flask-api-app
      Repository: https://github.com/labuser/flask-api-app

      DEPLOYMENTS:
      Total Deployments: 2
      - Environment: production
        Namespace: production
        Replicas: 3
      - Environment: staging
        Namespace: staging
        Replicas: 1

      DOWNSTREAM DEPENDENCIES:
      Total Dependencies: 1
      - api-gateway (owned by network-team)
      =========================================="
}
----

This is Concert's second unique contribution. The SBOM query told you *what* is affected; Arena View tells you *what breaks if you change it* — including services owned by other teams.

== Step 7: Watch the AO Switch Node Decision

With both Concert answers in hand, Automation Orchestrator — not Concert — makes the routing decision:

[source,text]
----
if production_deployment and severity in ['critical', 'high']:
    route = "auto-update"
elif downstream_dependencies > 0:
    route = "create-approval-request"
else:
    route = "queue-for-scheduled-update"
----

For `flask-api-app`, the switch node evaluates:

* **Production deployment?** → Yes (3 replicas in `production`)
* **Lightwell package severity?** → `critical` (fixes CVE-2026-52891)
* **Decision**: Auto-update

[NOTE]
====
The decision logic lives in Automation Orchestrator, not Concert. That separation matters: AO can factor in data Concert never sees — change freezes, business criticality tags, on-call state, OPA policy — without any change to Concert itself.
====

== Module Summary

You've completed Module 1! Here's what happened:

1. **Lightwell published a package** → Artifactory sent a webhook to EDA
2. **Event-Driven Ansible received the event** → Relayed it to the Automation Orchestrator webhook
3. **Automation Orchestrator queried Concert SBOM** → "Which apps are still on an older version?"
4. **Concert answered instantly** → 12 of 537 applications, including flask-api-app
5. **Automation Orchestrator queried Concert Arena View** → Production deployment, 1 downstream dependency
6. **AO switch node routed to auto-update** → Production + critical severity

**The Value of Concert**:

* **Speed**: Instant identification of affected apps (seconds vs. hours)
* **Accuracy**: SBOM-based correlation, not guesswork about what's deployed
* **Context**: Arena View shows cross-team blast radius before you change anything
* **Scale**: One package publish resolves to a complete, ordered work queue
