## Slide 2 — Patching is reactive, and slow

*Red subtitle:* The bottleneck is not the fix — it is knowing where the fix needs to go

- A CVE drops. Now what?
  - Which of our applications actually use the affected package?
  - Who owns them? What breaks downstream if we patch?
  - Someone opens a spreadsheet. Weeks pass.
- The industry average for remediating a critical dependency CVE is measured in **weeks**, not minutes.
- The bottleneck is not the fix. The bottleneck is **knowing where the fix needs to go** and **getting it there safely**.

*Side panel — the manual loop:* scanner flags a CVE → hunt for affected apps →
chase down owners → open tickets → manual PR + deploy → hope nothing broke.
**Elapsed: days to weeks.**

**Talk track:** Most vulnerability programs are a detection pipeline bolted onto a manual remediation process. We're going to invert that.

## Slide 3 — Start from the fix, not the flaw

*Red subtitle:* Move the trigger, and everything downstream changes

| Reactive (typical) | Proactive (this lab) |
|---|---|
| Trigger: a scanner finds a CVE | Trigger: Lightwell publishes a remediated package |
| "We have a problem" | "We have a solution — go apply it" |
| Hunt for affected apps | Concert already knows |
| Manual PR, manual deploy | Tekton builds, ArgoCD deploys |

- Red Hat **Lightwell** publishes a hardened, remediated build of a package into Artifactory.
- That publish event *is* the trigger. The fix arrives before anyone files a ticket.

**Talk track:** This is the key idea of the lab. Everything downstream follows from moving the trigger.

## Slide 4 — The cast: who does what

*Red subtitle:* Concert answers “who is affected?” — AO owns the decisions

| Component | Role in this lab |
|---|---|
| **Artifactory** | Package store — emits the webhook when a Lightwell package lands |
| **Event-Driven Ansible** | Always-on listener — turns the event into a workflow |
| **IBM Concert** | Pre-indexed SBOM inventory + Arena View dependency topology |
| **Automation Orchestrator** | The brain — routing decisions, approval gates, audit trail |
| **AAP** | The hands — playbook execution |
| **Tekton** | CI — build, test, image, GitOps manifest bump |
| **ArgoCD** | CD — GitOps sync to OpenShift, drift detection, rollback |

**Talk track:** Note what Concert is *not* doing. It is not orchestrating. It's a very fast answer to "who is affected?" AO owns the decisions.

## Slide 5 — Lab architecture

*Red subtitle:* From package publish to validated production deploy

Swimlane diagram. Two lanes — **Ansible Automation Platform** (top) and
**IBM Concert** (bottom) — with seven numbered steps flowing left to right.

**Step 1 spans the full height of both lanes.** The Artifactory publish is one
event that both lanes react to, so it is drawn as a single tall card feeding
right into both the Ansible lane and the Concert lane.

Every other column is filled in both lanes:

| # | Column | Ansible lane (top) | IBM Concert lane (bottom) |
|---|---|---|---|
| 1 | Package publish | **Artifactory** — `lightwell-remediated` repo emits webhook `[TRIGGER]` — *spans both lanes* ||
| 2 | Event detection | **Event-Driven Ansible** — rulebook matches, fires workflow | *alt:* **Concert ingest** — new Lightwell build indexed in the SBOM |
| 3 | Orchestration | **Automation Orchestrator** — owns routing, policy, audit | *alt:* **Risk prioritization** — ranks affected apps by exposure |
| 4 | Impact analysis | *alt:* **Automation Orchestrator** — could own the query and the policy gate | **SBOM inventory + Arena View** — 12 of 537 apps on an older build |
| 5 | Source update | **AAP playbook** — bump requirements, branch, commit, push | *alt:* **Concert Secure Coder** — safe-version fix, opens a pull request |
| 6 | Build & deploy | **Tekton + ArgoCD** — test, build image, GitOps sync | *alt:* **Concert Workflows** — change request, approval, tracked |
| 7 | Validation | **AAP validation** — 3/3 pods healthy, `/health` reports 6.0.2 | **SBOM updated** — portfolio drift 12 to 11 |

**Legend:** solid outline = the path this lab walks. Dotted outline (greyed
title) = the same step, owned by Concert — or by AO — instead. These are the
alternatives worth arguing about, not steps the lab actually runs.

Arrows: the main chain runs straight along the Ansible lane, 1 → 7. Column 4
carries a down/up pair (AO asks Concert who is affected, Concert answers).
Column 7 writes back down into Concert so inventory reflects reality.

> **Terminology check.** *Concert Secure Coder* is IBM's in-IDE / browser
> pre-commit remediation product — it flags vulnerable dependencies,
> recommends a safe version, and generates a pull request with the fix. IBM's
> own public demo repo shows it bumping a dependency to a **Red Hat Lightwell
> remediated build**, which is exactly this lab's shape.
> *Concert Workflows* is the documented auto-remediation mechanism
> (`Create_Change_Request_For_Remediation_Action`,
> `Monitor_Remediation_Action_Status`, `Remediation_Master`), which routes
> approvals through a GitHub PR or a ServiceNow incident.

**Footer:** The trigger is a fix being published — not a flaw being found.
Publish to validated production deploy in ~3 minutes.

**Talk track:** Walk it left to right. The thing to notice is step 1 — the trigger is a fix being published, not a flaw being found, and it lands on both lanes at once. Concert answers "who is affected" in one API call and gets written back to at the end. Everything in the top lane is Ansible orchestrating and executing, with Tekton and ArgoCD doing the actual build and deploy.

The dotted boxes are the conversation piece: Concert can own most of these steps itself — Secure Coder opens the fix PR, Concert Workflows drive the change request and approval. We run them through AAP here because that's where the policy and the audit trail live, but the split is a design choice, not a constraint. That question belongs on slide 9.

## Slide 8 — What to watch for

*Red subtitle:* Four moments that carry the whole argument

1. **The switch node.** That's where your policy lives. Change one condition and the whole risk posture changes.
2. **The Concert query latency.** One API call replaces a portfolio-wide scan. That's the entire value proposition in a single HTTP request.
3. **The ArgoCD sync.** Nobody SSH'd anywhere. Desired state went into Git and the cluster converged. Rollback is one command.
4. **The audit trail.** Every hop is independently queryable. This is what an auditor actually asks for.

## Slide 9 — Demo questions

*Red subtitle:* Where should this go next? We want your opinions.

Open questions — we want your opinions on where this should go next:

1. **Should we wrap everything in a ServiceNow ticket?**
   Auto-create a change record at the switch node, attach the Concert impact analysis and Tekton logs, close it on validation. Governance, or just latency?

2. **How do we make this more OpenShift-native — or give it its own pizzazz?**
   Should more of this run as OCP-native primitives? What would make the demo *memorable* rather than merely correct?

3. **Policy gates.**
   Where do OPA / Kyverno / ACS admission policies belong in this flow? Block the image at admission, or gate earlier in the pipeline? Who owns the policy?

4. **Red Hat Dependency Analytics.**
   Does RHDA overlap with Concert here, or complement it? Shift-left in the IDE vs. portfolio-wide inventory — is there a story where both run?

5. **Trusted Profile Analyzer.**
   Where does TPA fit for SBOM attestation and VEX? Should the Tekton pipeline emit a signed SBOM and push it to TPA, so the audit trail includes provenance, not just a version bump?

6. **Should prod ever be fully hands-off?**
   The one we keep arguing about. If an approval gate is always required — approval by whom, and on what evidence?
